# Papercut workflow

## Human overview

The papercut scheduling rule decides when, and by whom, one `capture` look runs. The skill is loaded even when no candidate is expected; no qualifying result returns `Papercut: none` without ledger access.

Discovery stays within the completed work and the bounded structured evidence it directly carries. Every distinct qualifying root cause is returned in authored-task order, then first qualifying observation order within each task; direct work uses observation order. There is no receipt escalation or numeric result cap. Equivalent symptoms consolidate before recording and return. Repository persistence remains opt-in through explicit `papercut init` or an exact approved `init-ask` effect; an initialized writable repository may record results automatically, while absent, unsafe, malformed, or unauthorized storage leaves every result report-only. Papercut creates no stage, second Handoff, eager ledger access, learning dispatch, or presenter-side invocation.

## Module design

The always-applied papercut scheduling rule decides when, and by whom, one `capture` look runs. `SKILL.md` owns bounded discovery, qualification, repository-ownership judgment, redaction, stable root-cause consolidation, all-result ordering, Learning Candidate construction, persistence, exact-record settlement, and disclosure. Discovery starts from the just-completed Handoff or direct verification evidence and may inspect only directly referenced dependency Handoffs, current-plan task/check/blocker records for that outcome, and other structured evidence explicitly carried by those artifacts. It never escalates through receipts or mines transcripts, history, memory, logs, trackers, timers, background state, or repository-wide inventories. `scripts/papercut_ledger.py` remains private mechanics with four operations: `init`, `list`, `record`, and `resolve`; stable identity remains `surface` plus `summary`, and the repository ledger stores compact v2 evidence only. `init-ask` may delegate one approved initialization call but owns no papercut semantics or storage. Papercut is never a task, Methods token, workflow or route stage, todo phase, assurance event, code/test review, or continual-learning trigger; capture changes no task state.

## Current flow

1. The papercut scheduling rule decides when, and by whom, one `capture` look runs.
2. Start from the completed work and its lean Handoff or direct verification evidence. Inspect only directly referenced dependency Handoffs, current-plan task/check/blocker records for that outcome, and structured evidence explicitly carried by those artifacts. No severity marker, recurrence marker, or receipt is required to inspect this bounded evidence, and none widens the boundary.
3. Discover all plausible friction, apply the unchanged material/repository-owned/reproducible/redactable qualification bar, and consolidate symptoms with the same stable surface and root-cause class. Order distinct causes by authored task order and then first qualifying observation within the task; direct work uses first qualifying observation order. A later successful attempt does not erase a stable qualifying cause.
4. If no cause qualifies, return exactly `Papercut: none` and do not inspect the ledger.
5. For every distinct qualifying cause, derive stable `surface` and root-cause `summary` plus redacted current evidence. If storage is absent, malformed, unsafe, or outside authority, keep every result report-only. Automatic capture never initializes or repairs storage.
6. With an initialized writable ledger, call `list` once and then `record` once for each distinct result in stable order. Do not retry a failed call; report that result and every unsafe-to-write remainder without dropping them. Return one compact line per distinct qualifying cause in the same order. There is no one-result cap.
7. Each qualifying result may independently form a complete Learning Candidate with its unchanged originating `PC-ID` when known. The current specialty adapter or direct lifecycle owner invokes portable `continual-learning` only when otherwise eligible; papercut itself never dispatches learning.
8. Settle each eligible unchanged originating `PC-ID` only from its authoritative candidate-specific result: durable correction maps to `fixed`, final candidate-specific rejection to `rejected`, and authoritative replacement to `superseded`. Blocked, incomplete, deferred, broad, global, or unrelated outcomes remain open. Resolution removes current observation prose; a later distinct recurrence reopens the same stable record and retains its latest resolution.

## Included, excluded, and deferred

Included: one deterministic look after every completed repository-work Handoff and after the direct non-workflow boundary; blocker-reporting Handoffs that preserve completed repository work; `Papercut: none` accounting without ledger access; bounded structured evidence carried by the completed work; every distinct qualifying root cause in stable authored-task order; stable surface/root-cause consolidation; explicit repository-ownership rationale; explicit opt-in through `papercut` or approved `init-ask`; redaction; semantic deduplication; compact evidence; proposal-only review; immutable candidate delivery; exact-record settlement; host-portable invocation.

Excluded: read-only work and work abandoned before a repository-work Handoff; candidate-triggered scheduling; severity- or recurrence-gated discovery; receipt escalation; one-result selection or numeric caps; task or plan state as identity; Methods; workflow, route, todo, assurance, or continual-learning stages; per-task learning dispatch; raw transcript, history, memory, provider-log, repository-wide, or session-wide mining; counts, exhausted budgets, authority revisions, attempt IDs, models, providers, paths, hashes, or timestamps as qualification proof or stable identity; one record per attempt; ordinary assertion failures; external provider or runtime behavior without a repository-owned prevention seam; intentional boundaries; concurrent or unattributed activity; harmless acknowledgements; one-off noise; background jobs; tracker or repair state; product, domain, or ADR authority; staging, shipping, or external effects; automatic repository initialization.

Deferred: generic repository agent memory and any new supported setup integration without an approved owner and observable seam.

## Authority and maintenance

Where the repository has an ADR index, it names the records that govern this module, generic engineering assessment qualification and the thin dev adapter projection, portable continual learning and completion, and the separate repository setup interface. Product and custom workflow owners retain their outcomes; papercut settlement cannot create or alter them. The ledger is evidence, never authority. When changing this module, synchronize the rule, skill, evals, workflow documentation, and current ADR projection; recheck the helper and update it only when its private mechanics change. Preserve the exact four-mode/four-operation interfaces, one `list` call per initialized capture look, one `record` call per distinct result in stable order, and clean removal of v1 command and sidecar contracts.
