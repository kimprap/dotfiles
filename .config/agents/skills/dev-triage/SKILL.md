# Engineering Triage

Turn raw external requests into trustworthy workflow intake without becoming a mandatory lifecycle phase, an implementation owner, or an issue-tracker state service.

## Intake and effect boundary

Require an explicitly named issue, pull request, or tracker query; the current tracker capability and project-specific label mapping; the current repository authority; and one requesting owner. A bare issue or PR reference resolves through the configured tracker. If no tracker capability or mapping is available, return the exact missing configuration and stop rather than inventing labels or installing a setup framework.

Triage applies to raw external requests. Tickets produced by `dev-ticketing`, an approved Executor Plan, or another current project-owned implementation graph are already workflow-ready and skip triage.

Reading tracker items and repository evidence is read-only. Label changes, assignments, comments, closing, reopening, or other tracker mutations are external effects and require exact human authorization covering the named item and actions. Every generated tracker comment starts with:

```text
> This comment was generated by an AI-assisted triage workflow.
```

## Categories, states, and phase projection

Use exactly one category and one state, mapped through the tracker configuration:

- Category: `bug` or `enhancement`.
- State: `needs-triage`, `needs-info`, `ready-for-agent`, `ready-for-human`, or `wontfix`.

Conflicting state labels stop for maintainer direction. The states project into the existing workflow rather than creating a fifth todo phase:

| Triage state | Workflow meaning |
|---|---|
| `needs-triage` | Intake is not yet qualified; no route or task becomes ready. |
| `needs-info` | `Authority / Design` is blocked on named reporter evidence or a human decision. |
| `ready-for-agent` | The brief has sufficient authority and observable acceptance for `dev-ask` to compose applicable `Authority / Design`, `Build`, `Assurance`, and `Completion` work. |
| `ready-for-human` | A named human-owned decision, access requirement, manual action, or implementation prevents agent readiness; identify its current phase and resume condition. |
| `wontfix` | Terminal intake outcome; no engineering route starts. |

## Procedure

1. **Gather current evidence.** Read the full item, comments, labels, author and dates; for a pull request also read the exact diff and review state. Reuse resolved prior triage notes and never re-ask answered questions.
2. **Check redundancy and prior decisions.** Search by domain concept for an existing implementation and inspect current project-owned rejection authority such as active ADRs or tracker decisions. Report where you looked. Do not impose an `.out-of-scope/` knowledge base on repositories that do not already own one.
3. **Recommend before mutating.** Present the category and state recommendation, relevant repository evidence, and whether the request is already implemented or conflicts with current authority. Wait for maintainer direction unless the invocation already names the exact desired state and effects.
4. **Verify the claim.** For a bug, exercise the reporter's reproduction when the environment is available; a hard unexplained defect may return a qualified `dev-diagnosing-bugs` route but triage does not diagnose or fix it. For a pull request, inspect and run the smallest relevant read-only or disposable check. Record `confirmed`, `not reproduced`, or `insufficient detail` with evidence.
5. **Interview only when needed.** When a candidate request needs human decisions, use `dev-grilling`: batch the whole current frontier in each round and continue until it is empty, the user pauses, or a named evidence/authority/no-progress blocker remains. Use `dev-domain-modeling` only for qualifying confirmed terminology or architectural decisions. Facts come from tools or bounded `dev-research`, not from the reporter.
6. **Produce the intake result.** `ready-for-agent` and `ready-for-human` receive the durable brief below. `needs-info` receives established facts plus specific unanswered questions. `wontfix` records the current authority and reason; durable rejection records remain owned by the repository's existing decision system.
7. **Apply only authorized effects.** Recheck the item and labels, then perform exactly the approved tracker actions. A quick state override skips grilling but not conflict detection, brief completeness, or the external-effect gate.

## Agent-ready brief

```markdown
## Agent Brief

**Category:** bug | enhancement
**Summary:** <one observable outcome>

**Current behavior:**
<observed baseline or current pull-request state>

**Desired behavior:**
<observable behavior, boundaries, failures, and preserved behavior>

**Stable interfaces:**
- <domain/interface contract rather than line numbers or brittle file instructions>

**Acceptance criteria:**
- [ ] <independently verifiable criterion>

**Out of scope:**
- <explicit boundary>

**Evidence:**
- <reproduction, repository lookup, prior decision, and uncertainty>
```

The brief is durable product/engineering intake, not an implementation recipe. `dev-ask` and downstream owners rebind current paths, identities, architecture, and verification seams before execution.

## Return

Emit one Common Handoff with the tracker item identity, category/state, evidence, exact external effects performed or `none`, brief identity when present, unresolved authority, and `route-impact: unchanged|changed`. `ready-for-agent` returns to `dev-ask` for route composition; `needs-triage` and `needs-info` return to `dev-triage`; `ready-for-human` returns to the named human owner; `wontfix` returns to `dev-ask` for terminal presentation. Triage never implements, verifies completion, merges, ships, or treats a tracker label as execution authority.
