## Question

Which source-verifiable patterns from Cursor's public skills repository, public Orchestrate plugin, and agent-swarm article are suitable inputs to a harness-neutral implementation backend? Record role boundaries, task and state models, dependency and context flow, handoff and integration behavior, verification discipline, adaptive cost or model-routing lessons, and license or attribution constraints; explicitly separate the public Git-based plugin from the unpublished internal SQLite swarm infrastructure.

## Answer

### Findings

**Source boundary (must remain explicit).** At the examined public revision (`cursor/plugins` [`ba7b590`](https://github.com/cursor/plugins/commit/ba7b5907843e1e21ec692418c180e1f912cbf7d3), 2026-07-26), **Orchestrate is a public Cursor plugin**, version 1.1.0, that drives Cursor cloud agents through the Cursor SDK and persists its run substrate as `plan.json`, `state.json`, `handoffs/*.md`, `attention.log`, Git branches, and optionally Slack visibility. [Plugin manifest](https://github.com/cursor/plugins/blob/ba7b5907843e1e21ec692418c180e1f912cbf7d3/orchestrate/.cursor-plugin/plugin.json) · [planner source of truth](https://github.com/cursor/plugins/blob/ba7b5907843e1e21ec692418c180e1f912cbf7d3/orchestrate/skills/orchestrate/references/planner.md)

This is **not** the internal SQLite experimental swarm described in Cursor’s article: that article says the newer swarm uses a newly built VCS and reports a peak of roughly 1,000 commits/second, whereas the public plugin expressly uses Git/disk, isolated cloud-agent branches, and explicit merge tasks. The available primary sources do not establish code identity or API compatibility between them; use article details as design evidence, not as an implementation specification. **[INFERENCE]** [Article—VCS](https://cursor.com/blog/agent-swarm-model-economics#A-version-control-system-for-agents) · [public branch/merge behavior](https://github.com/cursor/plugins/blob/ba7b5907843e1e21ec692418c180e1f912cbf7d3/orchestrate/skills/orchestrate/references/spawning.md)

* **Role boundaries.** Public Orchestrate separates a one-shot dispatcher, root/subplanners that publish and interpret work but do not code, isolated workers that complete one scoped task and hand off once, and verifiers that return evidence-based verdict handoffs. A subplanner recursively owns one slice and aggregates child results for its parent. [Skill roles](https://github.com/cursor/plugins/blob/ba7b5907843e1e21ec692418c180e1f912cbf7d3/orchestrate/skills/orchestrate/SKILL.md) · [planner rules](https://github.com/cursor/plugins/blob/ba7b5907843e1e21ec692418c180e1f912cbf7d3/orchestrate/skills/orchestrate/references/planner.md) · [verifier contract](https://github.com/cursor/plugins/blob/ba7b5907843e1e21ec692418c180e1f912cbf7d3/orchestrate/skills/orchestrate/prompts/verifier.md)
* **Public task/state/dependency model.** A planner-authored task has a name, type (`worker`, `subplanner`, or `verifier`), scoped goal, optional allowed/forbidden paths, acceptance, verification recipe, `startingRef`, dependencies, retry cap, PR flag, measurements, and provider model field; a verifier additionally names its target. Runtime rows record branch/ref, dependency list, agent/run lineage, attempts, handoff location, lifecycle (`pending → running → handed-off`, or error/cancelled/pruned), failure class, and verification quality. [Plan schema](https://github.com/cursor/plugins/blob/ba7b5907843e1e21ec692418c180e1f912cbf7d3/orchestrate/skills/orchestrate/schemas/plan.schema.json) · [state schema](https://github.com/cursor/plugins/blob/ba7b5907843e1e21ec692418c180e1f912cbf7d3/orchestrate/skills/orchestrate/schemas/state.schema.json)
* **Context and handoffs.** Siblings cannot communicate or read each other’s branches. A declared dependency is both a spawn gate and a semantic context edge: after upstream handoff, its body is pasted into the downstream prompt. Durable shared information should instead be committed to the base and referred to by path. This makes declared dependency edges, concise handoffs, and bounded fan-in substantive design controls rather than scheduling decoration. [Handoff propagation](https://github.com/cursor/plugins/blob/ba7b5907843e1e21ec692418c180e1f912cbf7d3/orchestrate/skills/orchestrate/references/handoffs.md) · [spawn contract](https://github.com/cursor/plugins/blob/ba7b5907843e1e21ec692418c180e1f912cbf7d3/orchestrate/skills/orchestrate/references/spawning.md)
* **Integration and failures.** The public plugin has no separate `integrator` node type: planners publish integration as an ordinary, dependency-gated worker task with named branches, conflict intent, and post-merge acceptance. Mechanical liveness belongs to the script; semantic recovery belongs to the planner. It creates synthetic failure handoffs when an agent terminates silently, classifies failure modes, leaves downstream work pending behind failed dependencies, and requires an explicit retry/repair/prune decision. [Merge and failure policy](https://github.com/cursor/plugins/blob/ba7b5907843e1e21ec692418c180e1f912cbf7d3/orchestrate/skills/orchestrate/references/handoffs.md) · [loop semantics](https://github.com/cursor/plugins/blob/ba7b5907843e1e21ec692418c180e1f912cbf7d3/orchestrate/skills/orchestrate/scripts/core/loop.ts)
* **Verification.** Verifiers must execute observable checks rather than review a diff, and report one of `live-ui-verified`, `unit-test-verified`, `type-check-only`, `verifier-blocked`, or `verifier-failed`, with per-criterion evidence. Worker measurement claims can also be rerun on the produced branch and drift logged; that detects disagreement but does not automatically decide acceptance. [Verifier prompt](https://github.com/cursor/plugins/blob/ba7b5907843e1e21ec692418c180e1f912cbf7d3/orchestrate/skills/orchestrate/prompts/verifier.md) · [measurement policy](https://github.com/cursor/plugins/blob/ba7b5907843e1e21ec692418c180e1f912cbf7d3/orchestrate/skills/orchestrate/references/handoffs.md)
* **Article-only internal-system lessons.** The article describes a planner/worker task tree, but adds internal mechanisms not present in public Orchestrate: planners retain design decisions and prevent duplicate subtree decisions; shared design documents have compile-checked code references; a neutral third party resolves merge conflicts; agents can flag megafiles for outside decomposition; review uses multiple decorrelated lenses; and a line-budgeted Field Guide’s index is injected into every new agent. [Article—coordination and review](https://cursor.com/blog/agent-swarm-model-economics#failure-modes-at-1000-commits-per-second) · [Article—Field Guide](https://cursor.com/blog/agent-swarm-model-economics#letting-agents-shape-the-environment)
* **Adaptive execution/model-economics evidence.** In Cursor’s SQLite experiment, workers consumed at least 69% of tokens (over 90% in most runs); similar quality across tested mixes came with widely different costs. The article attributes the saving opportunity to using scarce high-capability judgment for decomposition/design/trade-offs and lower-cost execution for already explicit instructions. This is experiment-specific evidence, not a portable model-selection rule. [Article—results](https://cursor.com/blog/agent-swarm-model-economics#results-across-model-mixes) · [Article—economics](https://cursor.com/blog/agent-swarm-model-economics#model-economics)

### Recommended candidate inputs

These are candidate **portable behavioral contracts**, not decisions about the local skill inventory or a final backend:

1. **Explicit work graph:** goal → scoped tasks → dependency edges → acceptance/verification recipe → terminal handoff. Make dependencies carry both readiness and the minimum upstream context a child needs; use a durable, repository-visible artifact for larger shared context. [Public plan schema](https://github.com/cursor/plugins/blob/ba7b5907843e1e21ec692418c180e1f912cbf7d3/orchestrate/skills/orchestrate/schemas/plan.schema.json) · [handoff propagation](https://github.com/cursor/plugins/blob/ba7b5907843e1e21ec692418c180e1f912cbf7d3/orchestrate/skills/orchestrate/references/handoffs.md)
2. **Non-overlapping responsibility boundaries:** planner owns scope, decomposition, and meaning; worker owns one bounded delivery; verifier independently establishes what was actually exercised; integrator is a distinct neutral task with an explicit conflict and post-integration verification policy. The public plugin supports the first three and makes integration a worker task; the article supports the neutral-conflict-resolver rationale. [Public role rules](https://github.com/cursor/plugins/blob/ba7b5907843e1e21ec692418c180e1f912cbf7d3/orchestrate/skills/orchestrate/SKILL.md) · [Article—merge conflicts](https://cursor.com/blog/agent-swarm-model-economics#merge-conflicts)
3. **Inspectable state and recovery:** retain a provider-neutral task state machine, attempts, dependency blockers, output location, failure classification, and operator attention record. Treat automatic retry as a bounded mechanical policy; keep retry/split/escalate/drop as a semantic decision. [Public state schema](https://github.com/cursor/plugins/blob/ba7b5907843e1e21ec692418c180e1f912cbf7d3/orchestrate/skills/orchestrate/schemas/state.schema.json) · [public failure recovery](https://github.com/cursor/plugins/blob/ba7b5907843e1e21ec692418c180e1f912cbf7d3/orchestrate/skills/orchestrate/references/planner.md)
4. **Evidence-bearing verification:** carry an outcome taxonomy that distinguishes live behavioral confirmation, targeted-test confirmation, compile-only evidence, environmental blockage, and demonstrated failure; require commands/observations and criterion-level evidence. Candidate evaluation scenarios can exercise success, blocked verification, synthetic worker failure, failed dependency, integration conflict, context propagation, and retry/escalation. [Public verifier contract](https://github.com/cursor/plugins/blob/ba7b5907843e1e21ec692418c180e1f912cbf7d3/orchestrate/skills/orchestrate/prompts/verifier.md) · [failure handoff policy](https://github.com/cursor/plugins/blob/ba7b5907843e1e21ec692418c180e1f912cbf7d3/orchestrate/skills/orchestrate/references/handoffs.md)
5. **Adaptive gating and routing boundary:** only construct a multi-agent subtree when the work has genuinely separable scopes, explicit interfaces/acceptance, manageable fan-in, and low path contention; otherwise retain one owner. Record capability/cost/latency/risk requirements as execution metadata and let an adapter select a provider model. The public plugin’s task `model` and concrete catalog are Cursor-specific metadata, while the article supplies the empirical reason to measure role-level quality and cost rather than hard-code a model choice. **[INFERENCE]** [Public spawn design](https://github.com/cursor/plugins/blob/ba7b5907843e1e21ec692418c180e1f912cbf7d3/orchestrate/skills/orchestrate/references/spawning.md) · [public model catalog](https://github.com/cursor/plugins/blob/ba7b5907843e1e21ec692418c180e1f912cbf7d3/orchestrate/skills/orchestrate/scripts/models.ts) · [article economics](https://cursor.com/blog/agent-swarm-model-economics#model-economics)

### Exclusions and cautions

* **Do not reproduce or claim parity with the article’s internal VCS/swarm.** Its high-throughput VCS, reconciler, compile-checked design references, and Field Guide are article-described internals, not public Orchestrate interfaces. The portable map may capture the behavioral problem (decision provenance, neutral integration, bounded shared context) without adopting its undocumented transport or storage. **[INFERENCE]** [Article](https://cursor.com/blog/agent-swarm-model-economics) · [public plugin structure](https://github.com/cursor/plugins/tree/ba7b5907843e1e21ec692418c180e1f912cbf7d3/orchestrate)
* **Keep Cursor transport out of shared behavior.** Cursor SDK calls, `CURSOR_API_KEY`, Bun CLI invocation, cloud-agent/VM/branch mechanics, Cursor agent/run IDs, Slack adapter/Andon reaction handling, GitHub PR tooling, and concrete model IDs/profiles belong in a Cursor adapter or runtime verification—not in a shared role contract. [Public dispatcher](https://github.com/cursor/plugins/blob/ba7b5907843e1e21ec692418c180e1f912cbf7d3/orchestrate/skills/orchestrate/references/dispatcher.md) · [Slack adapter](https://github.com/cursor/plugins/blob/ba7b5907843e1e21ec692418c180e1f912cbf7d3/orchestrate/skills/orchestrate/scripts/adapters/README.md) · [model catalog](https://github.com/cursor/plugins/blob/ba7b5907843e1e21ec692418c180e1f912cbf7d3/orchestrate/skills/orchestrate/scripts/models.ts)
* **Do not generalize the model claims prematurely.** The article is a four-hour SQLite-from-documentation experiment using a held-out SQL suite and manual post-run review; it reports useful hypotheses and measurements, not a general provider/model prescription or a final cost policy. [Experiment design](https://cursor.com/blog/agent-swarm-model-economics#the-sqlite-experiment) · [model-results caveat](https://cursor.com/blog/agent-swarm-model-economics#results-across-model-mixes)
