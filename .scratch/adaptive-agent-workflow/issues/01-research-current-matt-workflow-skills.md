### Recommended candidate inputs

These are **candidate procedures and boundaries only**—not a local inventory or naming decision.

1. **Use the router as a decision matrix, not an execution engine.** Reuse its predicates—small versus multi-session, foggy versus clear, broken versus feature work, prototype-worthy versus conversationally decidable—and keep the result as a portable stage selection contract. `[INFERENCE]` The single-user-facing-router role can remain independent of concrete installed skill names through an adapter mapping.
2. **Retain the Wayfinder artifact model for uncertain work:** destination, low-resolution map, one authoritative resolution per child ticket, explicit blockers/frontier, fog/out-of-scope separation, and `research`/HITL boundaries. Preserve the handoff to specification before construction; do not merge decision mapping with implementation.
3. **Make the portable pre-implementation interface explicit:** accepted intent → specification with user-confirmed test seams → approved vertical tickets with blockers → fresh-context implementation. The spec and ticket templates supply useful content contracts while tracker calls, `.scratch` paths, labels, and assignment mechanics stay adapter concerns.
4. **Carry forward feedback disciplines as independent worker contracts:** TDD’s seam/red-green rules, diagnosis’s feedback-loop gate and regression-test rule, and review’s independently reported Standards/Spec axes. `[INFERENCE]` The review axes are genuinely independent and can be parallelized; that does not justify parallelizing dependent implementation or planning work.
5. **Use research and handoff as durable-information boundaries:** primary-source-cited research feeds a decision; handoff redacts and points to existing canonical artifacts instead of copying them. Conflict resolution should similarly use original change intent and verification, not text-level marker removal.
6. **Keep human authority at source-defined decision gates:** grilling decisions, prototype evaluation, test-seam confirmation, ticket-breakdown approval, and incompatible-conflict trade-offs. `[INFERENCE]` This naturally supports the effort constraint that planners do not code, verifiers do not repair, and integration stays a neutral, separate task.

### Exclusions and cautions

- **Do not treat experimental upstream skills as stable inputs.** For this workflow, `batch-grill-me` is especially relevant but remains in `skills/in-progress`; the stable upstream primitive is serial questioning. `claude-handoff` is also in progress and explicitly Claude-background-agent-specific, so it is not a portable handoff contract.
- **Do not revive deprecated names.** Upstream’s deprecated bucket lists `design-an-interface`, `qa`, `request-refactor-plan`, and `ubiquitous-language` as skills the author no longer uses. [Deprecated index](https://github.com/mattpocock/skills/blob/ed37663cc5fbef691ddfecd080dff42f7e7e350d/skills/deprecated/README.md)
- **Separate shared behavior from execution metadata.** Upstream itself contains agent UI metadata such as `agents/openai.yaml`, whose `display_name`, description, and implicit-invocation policy are presentation/activation metadata—not lifecycle semantics. [Example adapter metadata](https://github.com/mattpocock/skills/blob/ed37663cc5fbef691ddfecd080dff42f7e7e350d/skills/engineering/ask-matt/agents/openai.yaml) `[INFERENCE]` Provider tools, model IDs, slash syntax, background-job transport, and concrete tracker APIs should remain adapters or verification configuration.
- **Respect the source’s scale boundaries.** Wayfinder is for a foggy effort exceeding one session and is planning-only unless Notes override it; `to-tickets` makes blockers explicit precisely so only independent frontier work can proceed. Do not infer a general multi-agent implementation orchestrator from either skill.
