# Portable adaptive agent implementation workflow

## Destination

A decision-complete map ready to collapse into one coherent workflow specification, then executable tickets, for a harness- and model-agnostic adaptive engineering path that accepts an approved external product brief or PRD, a settled engineering request, or a bounded engineering-maintenance objective; optionally establishes human-approved engineering requirements; and then proceeds through engineering specification, implementation, and completion, with one user-facing router, a separate implementation backend, and an exact migration inventory for `.config/agents/skills/`.

## Notes

Domain: portable Agent Skills workflow design and local skill curation.

Consult `grilling`, `domain-modeling`, `craft-skill`, and `craft-name`; use `eng-codebase-design` when defining the portable orchestration seams. Treat `/Users/kim/.dotfiles` as the source of truth and current upstream sources as evidence, not authority.

Standing decisions and preferences:

- Shared skill bodies describe capabilities and behavior without provider tool names, model IDs, spawning commands, waiting primitives, worktree syntax, or host-specific invocation syntax.
- Provider-specific transports and model choices are adapters or verification metadata, not shared product behavior.
- Default implementation is one agent. Escalate only to a small independent batch or a full orchestrator when interfaces, ownership, acceptance, and dependency edges are settled.
- Planners decide and decompose but do not code; bounded workers implement; verifiers report without repair; neutral integration is a separate task.
- Humans retain product, architecture, destructive, and scope decisions.
- Wayfinder ends at this resolved decision map. A separate specification pass must collapse the linked decisions before implementation tickets are derived.
- This map decides both the portable architecture and the exact local skill additions, prefixes, combinations, updates, retained entries, and removals.
- The single user-facing router and the implementation backend are separate cooperating skills.
- Do not create `CONTEXT.md`, `CONTEXT-MAP.md`, or ADRs implicitly. Their use is an explicit human decision because no canonical domain artifact currently exists in this repository.
- When market or product authority is unresolved, the router stops with a `PRODUCT AUTHORITY REQUIRED` handoff to the human product owner or a future separate product-development flow. `eng-requirements` may clarify only engineering-facing behavior, acceptance, scope, and constraints; it never performs product strategy.
- A product brief or PRD, when needed, belongs to the external product authority or future product flow. `eng-requirements` preserves that authority while establishing build-facing requirements; the later engineering specification owns architecture, interfaces, implementation decisions, and testing seams.
- Atlas at `/Users/kim/dev/atlas/app` is the user's dedicated research framework and intended durable evidence/topic-vault backend. The portable research discipline must account for it through an optional capability boundary rather than requiring Atlas in every repository or harness.
- The intended Atlas future includes scheduled bounded web discovery, durable source/topic synthesis, and later freshness-aware agent lookup. Current Atlas contracts and incomplete plans are evidence for integration design, not proof that the scheduler, complete façade, or broad retrieval already works.
- Research is optional supporting coverage, not the organizing spine of the adaptive engineering workflow.
- Cursor synthesis prioritizes the agent-swarm model-economics article, public `orchestrate`, durable skills under `cursor-team-kit/skills`, and `continual-learning`; another public Cursor directory requires a specific justified contribution. The separate pstack end-to-end workflow is excluded from inputs and reserved for comparison after this map is decision-complete.
- Continual learning is required in the final workflow. Its exact lifecycle position, curator authority, `AGENTS.md` scope selection, cadence, and noise controls remain a named decision; Cursor-specific hooks and state paths are adapter evidence only.
- User-level `AGENTS.md` is exclusively human-managed. No router, worker, verifier, integrator, continual-learning curator, hook, or adapter may modify it; cross-repository learning candidates may only be reported to the user.
- After the complete skill graph is implemented and initially verified, run one terminal duplicate/overlap, trigger, depth, ownership, and Matt-style instruction refinement task; re-verify the refined graph; only then create an on-demand canonical as-built overview under `eng-flow`. Use the same uppercase artifact basename convention for future departmental flow routers.
